# Debounce в Go: замыкание, горутины и mutex

Разбор по вопросам из практики: почему «локальный» `timer` всё равно может участвовать в гонке и зачем нужен `Lock`.

## Короткий вывод

1. Вызов `Debounce(...)` сам по себе безопасен: каждый раз свой `timer` и своя пара `call` / `stop`.
2. `timer` локальный по объявлению, но общий для двух возвращённых функций через **замыкание**.
3. Гонка возникает, когда **один и тот же** экземпляр (`call` / `stop`) вызывают из разных горутин одновременно.
4. `sync.Mutex` защищает участок с `timer` — и чтение, и запись.
5. Mutex решает **оба** случая: `call ‖ stop` и `call ‖ call` (и даже `stop ‖ stop`).

---

## 1. «Timer же локальная переменная — как она доступна между потоками?»

Локальность значит: снаружи `Debounce` имени `timer` нет.  
Это **не** значит «доступна только одной горутине».

Ключ — **замыкание (closure)**:

```go
func Debounce(...) (func(T), func()) {
    var timer *time.Timer   // одна переменная

    return func(arg T) {    // call видит timer
        // ...
        timer = time.AfterFunc(...)
    }, func() {             // stop видит тот же timer
        timer.Stop()
        timer = nil
    }
}
```

Когда `Debounce` возвращает функции, `timer` не исчезает: Go держит его в куче и привязывает к обеим функциям.

```text
        Debounce(fn, wait)
                │
                ▼
        ┌─────────────────┐
        │  timer  = nil   │   ← одна ячейка в куче
        └────────┬────────┘
                 │
        ┌────────┴────────┐
        │                 │
        ▼                 ▼
   call(arg)           stop()
```

Аналогия с JS: `let timerId` внутри `debounce` тоже «локальный», но общий для возвращённой функции через замыкание. В браузере обычно один поток JS; в Go горутин много — гонка реальнее.

---

## 2. Что безопасно, а что нет

### Безопасно: сам вызов `Debounce`

Каждый вызов `Debounce(...)` выделяет **свой** участок памяти. Два независимых экземпляра друг с другом не гоняются:

```text
Debounce() №1 → [timer₁] ← call₁, stop₁
Debounce() №2 → [timer₂] ← call₂, stop₂   // отдельно от №1
```

### Опасно: concurrent use одного экземпляра

`call` и `stop` могут быть вызваны «одновременно» из разных горутин. Изнутри Debounce это не контролировать (вызывающий сам решает, как звать API). Поэтому возникает гонка за **один** `timer`.

Мы *можем* договориться снаружи («только из одной горутины») — тогда mutex не обязателен.  
Библиотека этого не знает → либо mutex, либо в документации: *not safe for concurrent use*.

---

## 3. Что именно является гонкой

Mutex защищает общий `timer` от **любого** пересекающегося доступа:

| Сценарий | Гонка? |
|----------|--------|
| `call` ‖ `stop` | да |
| `call` ‖ `call` (две горутины) | да |
| `stop` ‖ `stop` | да (реже) |

Это **и то и другое вместе**: не только call vs stop, но и два параллельных `call`.

```text
call ──┐
call ──┼──► [ timer ]
stop ──┘
```

Типичный сценарий двух `call` без lock:

```text
горутина 1:  timer = AfterFunc(A)   // таймер A запущен
горутина 2:  timer = AfterFunc(B)   // указатель перетёрли, A не Stop()
             → A всё равно сработает + потом B
```

Схема по времени (`call` и `stop`):

```text
горутина A (call)          общая память            горутина B (stop)
─────────────────          ────────────            ─────────────────
читает timer ─────────────► [ timer = T1 ]
останавливает T1
                                   ◄─────────────── читает timer
пишет timer = T2 ─────────► [ timer = T2 ]
                                   ◄─────────────── Stop() / nil
                           кто победил — не определено
```

С `Lock`:

```text
A: Lock → работа с timer → Unlock
B: ждёт ... Lock → работа с timer → Unlock
```

Уточнение: горутины *могут* быть на разных OS-потоках, но гонка бывает и при чередовании на одном. Важно, что доступ к `timer` **не синхронизирован**.

---

## 4. Mutex блокирует и чтение, и запись

`sync.Mutex` — взаимоисключающая блокировка: кто взял `Lock`, тот один. Остальные ждут на `Lock`, неважно, хотели читать или писать.

В debounce под lock обычно всё вместе:

```go
mu.Lock()
// чтение timer, Stop, присваивание нового
mu.Unlock()
```

«Просто прочитать `timer`» без синхронизации тоже гонка, если другая горутина может его менять.

На будущее: `sync.RWMutex` позволяет нескольким читателям сразу, писатель один. Для одного указателя `timer` обычного `Mutex` достаточно.

---

## 5. Mutex Debounce ≠ ответственность обёрнутой `fn`

| Что | Чья ответственность |
|-----|---------------------|
| Безопасный доступ к `timer` / `call` / `stop` | Debounce (mutex или контракт «одна горутина») |
| Общие данные, которые трогает `fn` | сама `fn` / её вызывающий код |

`time.AfterFunc` запускает `fn` в **отдельной** горутине. Mutex вокруг `timer` **не** защищает внутренности `fn`. Если `fn` меняет общий state — синхронизация нужна там.

```text
Debounce lock  →  безопасные обновления timer / stop
fn / caller    →  безопасные обновления того, что мутирует fn
```

## 6. Пример с mutex (идея)

```go
func Debounce[T any](fn func(T), wait time.Duration) (call func(T), stop func()) {
	var (
		mu    sync.Mutex
		timer *time.Timer
	)

	stop = func() {
		mu.Lock()
		defer mu.Unlock()
		if timer != nil {
			timer.Stop()
			timer = nil
		}
	}

	call = func(arg T) {
		mu.Lock()
		defer mu.Unlock()
		if timer != nil {
			timer.Stop()
		}
		timer = time.AfterFunc(wait, func() {
			fn(arg)
		})
	}

	return call, stop
}
```

Для интервью / тестов из одной горутины mutex можно не ставить.  
Для библиотеки или многогорутинного использования — ставить.

## 7. Общий паттерн: не каждый return функции = Lock

**Неверно:** «функция возвращает другую функцию и есть замыкание → обязательно Lock».

**Верно:** Lock нужен, если выполняются **оба** условия:

1. в замыкании (в возвращённой функции / функциях) есть **мутация** общей переменной;
2. эти функции могут вызываться **одновременно из разных горутин**.

Формула:

```text
мутация в замыкании  +  concurrent use  →  Lock (или atomics / канал)
мутация в замыкании  +  одна горутина   →  Lock не обязателен
нет мутации (только чтение)             →  Lock не нужен
```

Важно: переменная должна **меняться именно в возвращённой функции** (или в нескольких, как `call` / `stop`), а не просто «лежать» локально снаружи без записи из замыкания.

| Ситуация | Lock? |
|----------|--------|
| Замыкание только читает неизменяемые данные | нет |
| Мутирует state, вызовы только из одной горутины | обычно нет (контракт) |
| Мутирует state + concurrent use | да |

Пример без Lock — `x` не меняется:

```go
func makeAdder(x int) func(int) int {
	return func(y int) int { return x + y }
}
```

Пример, где Lock нужен **при concurrent use** — мутация в возвращённой функции:

```go
func makeCounter() func() int {
	n := 0
	return func() int {
		n++      // запись в замыкании
		return n // чтение
	}
}
```

- одна горутина всегда вызывает этот `func` → Lock не нужен;
- несколько горутин зовут **один и тот же** `func` → Lock (или `atomic`) нужен.

Debounce попадает под опасный случай: `timer` **пишется** в `call`/`stop`, и API **могут** звать параллельно.
